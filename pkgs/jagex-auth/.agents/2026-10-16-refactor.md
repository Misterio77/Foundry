# jagex-auth hardening and standalone extraction

Date: 2026-10-16
Status: proposed; planning only, implementation not started

## Goal and scope

Make `pkgs/jagex-auth` a small, trustworthy browser-based Jagex-account
authentication helper for existing clients, without requiring another launcher.
Implement and validate it in Foundry first; extract the working project later.

It authenticates and launches compatible clients. It does not download clients,
update them, automate gameplay, or solve RS3's GTK2/OpenSSL 1.1 dependencies.
Do not modify `pkgs/runescape/default.nix` as part of this refactor.

## Current integration

- `pkgs/jagex-auth/jagex-auth.py`: Python-stdlib CLI with `authorize` and
  `handle-url`, browser login, character selection, and credential persistence.
- `pkgs/jagex-auth/default.nix`: package, hidden `rshub` desktop handler, and
  `passthru.wrapLaunch`.
- `pkgs/default.nix`: package export.
- `home/gabriel/features/games/runescape/default.nix`: wraps RuneLite, HDOS, and
  RS3; installs the helper and persists `.local/share/jagex-auth`.
- Credentials currently use Java-properties escaping but are sourced as shell
  code by `wrapLaunch`. These formats are incompatible; eliminate evaluation.
- Callback and credential writes use predictable temporary names, chmod after
  creation, and a shared callback slot. Concurrent logins can interfere.
- State and nonce are checked, but JWT payload decoding does not verify a
  signature. The precise server/local validation boundary needs review.

## Proposed CLI contract

Preserve:

```text
jagex-auth authorize
jagex-auth handle-url URL
```

Add:

```text
jagex-auth launch -- COMMAND [ARG ...]
```

`launch` is noninteractive. It reads and validates stored credentials, adds
`JX_SESSION_ID`, `JX_CHARACTER_ID`, and `JX_DISPLAY_NAME` to a copy of the current
environment, then uses `os.execvpe`. Preserve argument boundaries, other
environment variables, signals, and the client's exit status. Saved credentials
override inherited values for these three keys. Never evaluate credential data
as code or put it in process arguments or the Nix store.

Missing, malformed, or unusable credentials fail with an actionable error asking
the user to run `jagex-auth authorize`; do not silently launch unauthenticated or
start a browser. Missing command and executable/permission failures also need
clear errors and conventional nonzero exit codes.

Do not add refresh flows, an interactive launcher UI, automatic login on launch,
or a multi-profile credential store in this iteration.

## Phase 1: establish project layout and tests in Foundry

- [ ] Keep sources under `pkgs/jagex-auth`, with an importable implementation,
  thin CLI entry point if useful, and a `tests/` directory. Avoid unnecessary
  packaging/framework churn; a small stdlib-only application is the baseline.
- [ ] Add deterministic tests using temporary XDG directories, mocked browser
  and HTTP interactions, and synthetic tokens. Never read real credentials or
  contact Jagex in automated tests.
- [ ] Record current protocol expectations and CLI behavior before changing them.
- [ ] Arrange source selection so tests/docs ship as source and tests can run in
  the Nix derivation's check phase.

## Phase 2: safe credential storage and process launch

- [ ] Replace the properties file with versioned structured JSON, for example
  `$XDG_DATA_HOME/jagex-auth/credentials.json` (defaulting to
  `~/.local/share/jagex-auth`). Validate schema and nonempty string values.
- [ ] Keep the data directory private (`0700`). Use unique temporary files
  created with mode `0600` from the outset, atomic replacement in the same
  directory, and cleanup on failure. Refuse unsafe file types/paths as
  appropriate; document that this does not defend against a compromised process
  running as the same user.
- [ ] Implement `launch` with explicit argument parsing and `os.execvpe`.
- [ ] Prefer explicit reauthorization over an automatic legacy parser: if only
  `credentials.properties` exists, explain that the format changed and request
  `authorize`. Never source or evaluate it. Document when the obsolete secret
  file can be deleted; do not silently destroy it on a failed authorization.
- [ ] Keep secrets out of errors, logs, test snapshots, and subprocess arguments.
  Avoid dumping raw HTTP response bodies that might contain authentication data.

Tests: round-trip Unicode and shell metacharacters literally (including `$()`,
backticks, quotes, backslashes, spaces, and newlines where permitted); invalid
schemas and empty fields; missing/legacy storage; file permissions and failed
writes; unchanged prior credentials after failure; exact child argv/environment;
child exit status and signal behavior using a harmless test executable.

## Phase 3: authentication and callback hardening

- [ ] Review the actual Jagex/OIDC flow and published issuer metadata before
  choosing validation changes. Do not assume that exchanging an ID token proves
  every local check is unnecessary, or that an unverified payload is trusted.
- [ ] Document the token trust boundary: which checks the session endpoint is
  known to perform, what is checked locally, and what remains unverified.
- [ ] Validate appropriate issuer, audience, expiry, and nonce claims against
  authoritative protocol information. If local signature verification is needed,
  use a maintained JOSE implementation and JWKS handling rather than hand-rolled
  crypto; explicitly revisit the stdlib-only goal and document the dependency.
- [ ] Reassess raw-token paste support: it bypasses URL state validation today.
  Retain only with a documented, validated nonce/token-binding story; otherwise
  keep successful-login URL paste as the supported manual fallback.
- [ ] Require exact supported callback/success URL shapes, unambiguous state and
  token fields, and sensible input size limits. Reject duplicate critical fields,
  malformed JWTs, unexpected claims, and provider errors without leaking secrets.
- [ ] Introduce bounded authorization waiting with actionable timeout/cancellation
  behavior and cleanup of pending state.
- [ ] Define concurrency explicitly. Prefer one active authorization per data
  directory with a process lock and clear second-login failure, plus callbacks
  tied to that attempt's unpredictable state. `handle-url` must reject unsolicited
  or mismatched callbacks without overwriting the active attempt's response.
- [ ] Use private, uniquely created temporary callback files and atomic writes.
  Clean stale attempts safely; do not delete another live attempt's files.
- [ ] Ensure pasted input and desktop callbacks undergo equivalent validation.
  Keep the browser callback path usable when stdin is closed/noninteractive.

Tests: valid flow; state/nonce mismatch; invalid URL host/path/scheme; duplicate
fields; malformed/oversized payloads; expiry/audience/issuer cases selected by the
protocol review; unsolicited/stale callbacks; concurrent authorizations and
callback races; timeout/interruption cleanup; HTTP/network/JSON failures; failed
reauthorization preserving existing credentials; character selection errors.

## Phase 4: Nix integration

- [ ] Change `passthru.wrapLaunch` to execute the packaged `jagex-auth launch --`
  followed by the original client executable and original arguments. Use store
  paths and preserve the original package's desktop integration and metadata.
- [ ] Remove all shell sourcing and `set -a` credential handling. Avoid recursive
  wrappers or symlink writes into the original package output.
- [ ] Keep the existing Foundry call sites working for RuneLite, HDOS, and RS3.
  Preserve handler installation and XDG persistence requirements.
- [ ] Add a wrapper integration check using a fake client, synthetic credentials,
  and a temporary HOME/XDG directory; verify desktop Exec entry points still
  resolve to wrapped binaries, with no credentials embedded in outputs.
- [ ] Enable automated Python tests in the derivation. Format only changed Nix
  files with Alejandra (`nix fmt <changed-files>`).

## Phase 5: documentation and local acceptance

- [ ] README: purpose, supported/tested clients, Python requirements, direct
  non-Nix usage, Nix installation, browser handler registration, authorization,
  launch, `wrapLaunch`, storage/migration, session expiry and reauthorization,
  troubleshooting, security model, and unofficial/non-affiliation disclaimer.
- [ ] Add a real MIT license file after confirming copyright attribution.
- [ ] Document that a game session is sensitive, there is no automatic refresh,
  and environment variables are not protection against same-user processes.
- [ ] Review authentication-sensitive code independently before public release.
- [ ] Build the helper and wrapped-client checks; evaluate Foundry's affected
  Home Manager configuration. Do not rebuild/deploy the system without approval.
- [ ] User-operated smoke test: browser authorization and callback, character
  selection, RuneLite launch; test HDOS/RS3 where available. Distinguish client
  runtime problems from authentication failures. Never capture real tokens in
  agent context. Agree handler registration changes before applying them.

Acceptance gate before extraction:

1. Automated tests pass without network access or access to real credentials.
2. No credential file is evaluated by a shell; adversarial strings stay data.
3. Safe file modes, atomic writes, callback binding, and concurrency are tested.
4. Authentication validation decisions and any residual limitations are explicit.
5. Nix wrapper checks pass, existing call sites remain compatible, and a real
   user-operated login/client launch succeeds.
6. A new user can follow the README without knowing Foundry's internal layout.

## Phase 6: extract only after the Foundry version is accepted

- [ ] Choose standalone repository name/location and source layout with Gabs.
  Preserve provenance/history where practical; do not create/push a remote yet.
- [ ] Move the accepted source, tests, docs, and license together. Avoid two
  independently maintained implementations.
- [ ] Provide a standalone flake with `packages`, `apps`, `checks`, and a small
  development shell for supported platforms. Keep ordinary Python usage viable.
- [ ] Expose `wrapLaunch` from the standalone package so consumers retain the
  same integration pattern. Include handler registration instructions; installing
  a desktop file does not itself guarantee it becomes the default URL handler.
- [ ] Wire Foundry to the chosen standalone source/input and remove the duplicate
  implementation. Review any lockfile changes and their upstream contents.
- [ ] Tag an initial release after verification; consider nixpkgs submission with
  a maintainer, tests, license, and clear scope. The helper should not depend on
  packaging the unsupported RS3 runtime.

reviewable stages after approval. Follow repository jj preflight and attribution
